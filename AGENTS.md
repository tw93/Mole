# Mole CLI (Linux) Agent Guide

This is the `linux` branch of `tw93/Mole`: **Mole CLI (Linux)**, a terminal cleaner for Linux desktops used by developers. It is developed like the `windows` branch (Mole CLI (Windows)): its own code, its own tests, its own release tags. Nothing here is shared with `main` (Mole CLI (macOS)) at runtime; the Go TUIs under `cmd/` were forked from `main` at the branch point and evolve independently. Rules, product values and safety contracts transfer by deliberate re-implementation, recorded in `SYNC.md`, never by importing macOS code (maintainer 2026-11-01: the two platforms clean different things and shared code breaks easily).

Status: pre-release. The branch stays unannounced until the first usable version (the MVP below) works on Omarchy; then README, release and the reply on tw93/Mole#1371 change together (maintainer 2026-11-01).

## Product names

Use **Mole Mac**, **Mole for Windows**, **Mole CLI (macOS)**, **Mole CLI (Windows)** and **Mole CLI (Linux)** exactly. Never an unqualified "CLI" or "Linux version" where the product is ambiguous.

## Scope

Six commands: `clean`, `uninstall`, `optimize`, `analyze`, `status`, `purge`.

- First target: Omarchy (Arch + Hyprland, Wayland). Other Arch-based systems come along. Debian/Ubuntu and Fedora rules come later; on those systems the package-manager items simply do not appear while user-level features work.
- First public version (0.1.0): `clean`, `uninstall`, `optimize`, `analyze`, `status`, plus `update` and `remove` for Mole itself, usable on Omarchy. `purge` was moved out of it and prints "not in Mole CLI (Linux) yet"; `optimize` was pulled into it because the release is not complete without it (both maintainer 2026-11-01).
- `optimize` uses no sudo. It changes only the user's font cache, launcher index, personal icon theme caches and the SQLite files of closed browsers and Thunderbird (Chromium family: History, Favicons, Web Data, Top Sites, Shortcuts, never Cookies or Login Data; Firefox, Zen and Thunderbird: every top-level `*.sqlite` except `cookies.sqlite`) (read through `mode=ro&immutable=1` so a dry run leaves no `-wal`/`-shm` behind, quick_check first, VACUUM only when 1MB or more comes back, never above 100MB, never through a symlinked profile or file, and the running-browser probe is asked again before each file; a browser that runs or a probe that cannot tell skips it); everything that would need root or a choice (failed units, broken launchers and autostart, `pacman -Qtdq`, a stale `db.lck`, only when no package manager runs under any user, root included, TRIM, two power managers) is reported with the command to run. A systemd question with no running systemd (`/run/systemd/system`) or no user bus is "unavailable", never "healthy". Its report-only items also cover Hyprland start commands, user unit programs and dangling `wants` links that point at missing programs, and root-owned files in `$HOME` and `~/.config`. Unused Flatpak runtimes belong to `clean`: `flatpak uninstall --user --unused` without sudo; the system installation is only reported with `sudo flatpak uninstall --system --unused`, since under sudo flatpak may not see the user's per-user apps.
- Not built: GUI, paid tier, background agents, schedulers, notifications, package upgrades, `autoremove`, emptying whole package caches, kernel removal, CPU governor / EPP / turbo / `platform_profile` / sysctl / `drop_caches` tuning. When TLP, power-profiles-daemon, tuned or auto-cpufreq is active, Mole only reports it.

## Safety contract

Every rule below is a design requirement for code that does not exist yet; each needs a test before the code that relies on it ships.

- **No root path deletion.** Mole never runs `rm`, `find -delete` or a move on an arbitrary path as root. Root-level cleanup happens only through the distribution's own command with a bounded scope: `paccache -rk2` (never `-rk0` or `pacman -Scc`), `journalctl --vacuum-time=` with a retention floor (never `--vacuum-size=1`), and in uninstall `flatpak uninstall` of the one system or custom-installation app the user picked. Package-manager locks (`/var/lib/pacman/db.lck`) present means the item is skipped.
- **Trash by default, XDG spec.** User files go to `$XDG_DATA_HOME/Trash` (default `~/.local/share/Trash`): write `info/<name>.trashinfo` with `O_EXCL` first to reserve the name, then rename into `files/`, and roll back the info file if the rename fails. Items on another filesystem go to that filesystem's `$topdir/.Trash-$uid` or are refused; never copy a tree across devices and delete the source. `gio trash` is a fallback, not the primary path. Permanent deletion is an explicit choice. One sink each: `internal/xdgtrash` (reached from bash through `bin/trash-go`, from analyze directly) for user files and uninstall leftovers, and `mole_remove_cache` in `lib/core/delete.sh` for the children of an allowlisted cache root in `lib/clean/rules.sh`, which are removed directly because moving a cache to the Trash frees nothing. Emptying the Trash is part of `clean`. A Trash move counts only on the helper's own `ok` line per path; a helper that cannot run is a failure, never a completed move.
- **Exact ownership only.** Clean deletes from an allowlist of known caches; unknown directories under `~/.cache` are listed (the five largest over 100MB, sizes only), never selected. A rule's owners are process names (`pgrep -x`), `cmd:<ERE>` (`pgrep -f`, for IDEs started as `java`) or `flatpak:<id>`; a rule may carry a selector (`versions:` keeps the active and newest other version, `obsolete`, `suffix:`, `tool:uv` runs `uv cache prune` instead of removing). Rules that hold user state are narrowed, never widened: JetBrains only `log/` (LocalHistory lives beside it), Deno only `deps remote gen npm registries`, Bazel only `cache/repos`. A redirected cache folder (a `~/.cache` symlink or `XDG_CACHE_HOME` outside home) is reported once and left alone. `mo clean --whitelist` keeps rules or paths in `$XDG_CONFIG_HOME/mole/whitelist` (rule labels, `/` and `~` paths and globs; labels because one label covers many profile folders); a path also keeps a single child of a rule that matches it or holds it (`~/.npm/_cacache/*` works as on Mole CLI (macOS)); an unreadable whitelist stops clean. Uninstall leftovers match exact identifiers (`~/.config/<id>`, `~/.cache/<id>`, `~/.local/share/<id>`, `~/.var/app/<id>`, `<id>.desktop`, `~/.config/systemd/user/<id>.service`, `~/.config/autostart/<id>.desktop`), never substrings or vendor wildcards. Also exact: `~/.<id>`, a fixed alias table (Arch `code` is `~/.vscode-oss`, `visual-studio-code-bin` is `~/.vscode`), Flatpak overrides, yay/paru build folders by pkgbase that contain a PKGBUILD, and `.timer`/`.socket` units. A path another installed app also maps to is never offered, and shared names (fontconfig, systemd, steam and the like) are never leftovers. User units are `systemctl --user disable --now`ed before they move to the Trash; with no user bus they stay where they are. The one extra ID is a launcher's `StartupWMClass` (often the config folder: `Code`, `obsidian`), and only when exactly one launcher on the system declares it and it is not a runtime's class (Electron, Java, Wine, Python). A Flatpak sandbox home is an orphan only when `flatpak list --app` succeeds and no installation has the app; without flatpak nothing is reported. AppImage launchers in `~/.local/share/applications` count as apps: the launcher, the AppImage file and its icon go to the Trash together.
- **Running owners block deletion.** Every rule names its owning executable or lock file; while it runs, the rule is skipped. `pgrep -x` cannot see names over 15 bytes (procps-ng 4 returns 1, "not running"), so longer names are matched on the 15-byte `comm` prefix and confirmed by the exe or argv[0] basename; a pacman app also counts as running when a process's exe or argv names a file from `pacman -Qlq`, which catches wrappers such as `code` on Electron (`--opt=/path` tokens count by their path). A process is the user's by the real uid on its `/proc/<pid>/status` `Uid:` line, never `-O /proc/<pid>` (a non-dumpable process such as KeePassXC has a root-owned folder); when its exe cannot be read, its `comm` matching the 15-byte prefix of a candidate executable answers 2. An unreadable file list returns 2 and blocks; the `versions:` selector selects nothing when `/proc` cannot be read. `/tmp` and `/var/tmp` cleanup touches only regular files owned by the user, on the same device, not open per `/proc/*/fd`. Clean has no `/tmp` rule today: Arch and Omarchy mount `/tmp` as tmpfs, emptied at every boot (checked on the VM 2026-11-01). Flatpak app caches (`~/.var/app/<id>/cache`, never the app's other folders) ask `flatpak ps` whether the app runs.
- **Never touched:** live logs in `/var/log`, package databases and their locks, `~/.cache/doc` (Flatpak document portal), model stores (`~/.ollama`, `/var/lib/ollama`, `~/.cache/huggingface`, `~/.cache/lm-studio`) unless the user picks them in a review list, mount points, `/boot /usr /bin /sbin /lib* /etc /var/lib /proc /sys /dev /run /nix/store`.
- **Uninstall delegates removal of the package to its owner** (pacman, yay/AUR, flatpak, later apt/dnf/snap) for the one package the user picked, keeping the owner's own confirmation (no `--noconfirm`, no `-y`). Web apps (Omarchy's `.desktop` launchers plus icons of any image type) and Omarchy TUI launchers are listed as such, not packages. Flatpaks are removed from their own `--installation`; a system or custom installation through `sudo` after `mole_sudo_ready`. Web app and TUI launchers leave only their launcher and icon, never the program's config, state or cache. `--with-data` shows browser (Chromium and Gecko families, Waterfox, Floorp, Tor and Mullvad Browser included) and mail profiles and offline music without preselecting them. After launchers go, the desktop database and user icon caches are refreshed; stale `mimeapps.list` entries are reported, not rewritten. Config and data leftovers are unchecked by default; caches are checked.
- **Dry-run and log.** Every destructive command has a dry-run that lists exactly what the real run would touch, and every change appends one operations.log row.
- **Parse structure, not words.** Run external tools with `LC_ALL=C` before parsing their output, prefer exit codes and machine formats (`findmnt -J`, `--porcelain`), and never match localized error text: the Omarchy test VM runs in Chinese and `du` prints 「权限不够」.
- **GNU tools only.** This branch targets GNU coreutils and findutils; no BSD spellings (`stat -f`, `find -flags`, `du -I`, `sed -i ''`).
- **Refuse root.** Mole runs as the desktop user and asks for sudo only for the bounded root items above. It asks once, before work starts, on Mole's own line (`mole_sudo_ready`: a purple arrow `Password:` passed to `sudo -p`, so sudo and PAM still read the password and Mole never holds it); clean offers Enter continue, Space skip, ESC cancel like Mole CLI (macOS), a keepalive spans the run, and `mole_sudo_end` drops only a timestamp Mole created. Outside a terminal it never prompts. Maintainer 2026-11-01: sudo's bare `[sudo] password for` appearing after the cleanup read as broken.

## Analyze and status

- Volumes come from `/proc/self/mountinfo`, read again at the start of every scan and every `du` run; a scan root reached through a symlink (`/home -> /var/home`) is resolved with `filepath.EvalSymlinks` before it is compared. Walkers and `du` enter local block-device mounts (a `/dev/` source: ext4, xfs, btrfs, vfat, LUKS) and btrfs subvolumes of the same filesystem; network, FUSE, 9p/virtiofs, overlay, tmpfs, squashfs and pseudo mounts show as "mounted, not scanned" and stay out of `du`, which runs without `-x` and excludes `.snapshots`. On btrfs, decide "same filesystem" by mount source plus fstype, not `st_dev` (each subvolume has its own). On noatime mounts "unused" reads the later of atime and mtime. Snapshots (`/.snapshots`, snapper, Timeshift) are counted, never scanned. Hardlinks are keyed by `(dev, ino)` and counted once.
- Status reads sysfs and procfs without root: `/sys/class/power_supply` (Battery and UPS, `energy_*` else `charge_*`), hwmon and `thermal_zone*` temperatures, `/sys/class/dmi/id` (treat `Default string`, `To be filled by O.E.M.`, `QEMU` as unknown), `/proc/pressure/memory` and swap for memory pressure. Health scoring must read memory pressure; a restart recommendation needs a Linux-specific basis or is not shown.

## Test environment

- LazyCat devbox (Debian 12 container, `linux-devbox` skill): run tests as the non-root user `mole` (`su mole -c "bats ..."`), since Mole refuses root. Go runs on the Mac: build with `GOOS=linux` (or `go test -c`) and execute the binary there.
- Omarchy: the Try Omarchy VM on the ThinkPad (lease `thinkpad`), reached from the Mac with `ssh -F ~/.config/mole-omarchy/config mole-omarchy` through the ThinkPad hop. The guest runs a user-level sshd (systemd user unit `mole-sshd`, port 2222, key only); the host-side forward `127.0.0.1:2222` is a runtime QMP `hostfwd_add n0 tcp:127.0.0.1:2222-:2222` and must be re-sent after every VM restart. No sudo password is available there: tests run as the desktop user, bats and shellcheck 0.11 live in `~/.local/bin` and Go in `~/.local/opt/go` (PATH in `.bashrc`, GOPROXY goproxy.cn), so the full gate runs there natively. Password flows are tested in the devbox instead, with a throwaway password and sudoers entry for its user `mole`, both removed afterwards. The guest locale is Chinese, which is the point: parsing must survive it. Its root is ext4 and `/tmp` is tmpfs; the devbox's overlay sits on btrfs. Go fixtures in `t.TempDir()` land on `/tmp` on both, where directories take no blocks, so a size that depends on a directory's own block only shows on the GitHub runner (ext4). Interactive screens are driven with tmux (`send-keys`, `capture-pane`), never over `ssh -tt`.
- Bash tests: `tests/*.bats` (bats 1.x), each test in its own HOME with fakes for `flatpak`, `pgrep` and the Trash helper first on PATH. Run `bats tests/` as a normal user after `make build`.
- CI: `.github/workflows/test.yml`, Linux runners only: shellcheck, `go test ./cmd/... ./internal/...` and bats inside an `archlinux` container as the user `mole`. No macOS jobs on this branch.

## Releases

- Tags are `V<version>-linux` (first: `V0.1.0-linux`), the same shape as the `windows` branch's `V<version>-windows`. A tag runs only the workflows in its own commit, so `main`'s `V*` release workflow never sees it. `VERSION` holds the version; the workflow refuses a tag that disagrees.
- `.github/workflows/release-linux.yml` runs the tests, builds `mole-<version>-linux-{x86_64,aarch64}.tar.gz` and `SHA256SUMS.txt` with `scripts/build-release.sh`, installs the archive for a fresh user, and creates a **draft** with `make_latest: false`: macOS installs read `releases/latest`, so a Linux release must never become it. The maintainer reads the draft and publishes it.
- `install.sh` (served from this branch at `raw.githubusercontent.com/tw93/Mole/linux/install.sh`) takes the newest exact `V*-linux` tag from the releases list, checks the archive against `SHA256SUMS.txt`, unpacks into `~/.local/share/mole` beside the old copy, runs it, then swaps it in and links `~/.local/bin/mo`. `mo update` reruns a copy of it (skipping prerelease tags, refusing to run from a tree that is not the installed one, `--force` reinstalls but never downgrades an installed version newer than the latest release; the main menu, only in the installed tree (`mole_runs_installed_tree`, the same check), checks for a newer release in the background at most once a day, cached in `~/.cache/mole`, off with `MOLE_NO_UPDATE_CHECK=1`); `mo remove` deletes only that tree, the two links when they point at it, and Mole's own config, cache and state folders.
- Before tagging: the Test and Secrets runs on the commit to be tagged are green (`gh run list --repo tw93/Mole --branch linux --commit <sha>`).
- Publishing the draft: GitHub ignores `make_latest` while a release is a draft and defaults it to true when it is published, and the web page's "Set as the latest release" box can be ticked. Publish only with `gh release edit V<version>-linux --repo tw93/Mole --draft=false --latest=false`, then confirm `gh api repos/tw93/Mole/releases/latest --jq .tag_name` still names a macOS tag (no `-linux`); if it does not, run `gh release edit <that macOS tag> --repo tw93/Mole --latest` at once.
- No tag, release or announcement without the maintainer's explicit go-ahead; publishing also changes README links and the reply on tw93/Mole#1371.
