# Mole CLI (Linux) ledger

What has been decided, shipped, verified and left open for Mole CLI (Linux), in one place. Contracts live in `AGENTS.md`, cross-product rows in `SYNC.md`, studies in `docs/oss-research.md`; this file links them by date and does not repeat them. Add a line here whenever a release, a maintainer decision, a measurement or an open item changes.

## Decisions (maintainer)

| Date | Decision | Rejected alternative |
|---|---|---|
| 2026-11-01 | Name: Mole CLI (Linux), matching Mole CLI (Windows). Free and open source, no GUI, no paid tier. | A paid Linux edition: Linux users pay rarely, and the value is reach among developers. |
| 2026-11-01 | Its own `linux` branch, like `windows`, re-implementing rules rather than sharing `main`'s code. | One branch with per-platform dispatch: any BSD/GNU difference (`stat -f` above all) could silently disable a safety check, and devbox tests showed it. |
| 2026-11-01 | First target Omarchy (Arch + Hyprland), then other Arch systems; apt, dnf and zypper rules come later, and on those systems the package items simply do not appear. | Debian/Ubuntu first. |
| 2026-11-01 | Scope: clean, uninstall, optimize, analyze, status; purge deferred. `completion` and `history` left out; `mo update` required. | Shipping purge in the first release. |
| 2026-11-01 | Go public once the first usable version is done, with optimize inside it ("without it the product is not complete"). | Releasing clean, uninstall, analyze and status first and optimize in the next version. |
| 2026-11-02 | Publish V0.1.0-linux with Flatpak verified only against a fake `flatpak` as a known residual. | Waiting for a machine with real Flatpak (it was verified later in CI). |
| 2026-11-02 | 0.2.0: everything from the second study round (snapshot honesty, cache rules, xdg-ninja leftovers, optimize reports, status grouping). | Splitting it over several minor versions. |
| 2026-11-02 | No logo on the macOS README (it already has a large header image); the Windows and Linux READMEs show the round app logo. | Adding the logo to all three. |
| 2026-11-02 | 0.3.0 aligns with Mole CLI (Windows): purge, history, GPU shader caches only with `--gpu-shaders`, `--debug` session log. | Shipping purge alone; keeping shader caches in the default clean. |
| 2026-11-02 | 0.4.0 covers Debian and Ubuntu: apt autoclean as a sudo item, Snap revisions reported, apt and Snap apps in uninstall, apt reports in optimize (decide 1102-26). | Deleting apt's cache as root, removing old kernels or autoremoving (ubuntu-cleaner's way); removing Snap's rollback revisions. |
| 2026-11-04 | `mo update --nightly` installs the newest `linux` commit from source like Mole CLI (macOS), building the Go helpers; when the user has no usable Go, Mole downloads a checksum-checked Go into its own cache for the nightly only, never for stable installs. | A rolling `nightly-linux` prerelease of built archives (a permanent entry on the repository's Releases page); installing Go through the package manager (needs sudo). |
| 2026-11-02 | AUR package `mole-cli-bin`: prepared, then held because AUR registration is paused. | Homebrew on Linux (the `mole` formula is macOS-only), AUR names `mole` and `mole-bin` (taken by an unrelated SSH tunnel tool that ships `/usr/bin/mole`). |

## Verification record

- **Omarchy VM** (Try Omarchy, Arch, ext4, Chinese locale): every 0.1.0 and 0.2.0 command run for real, each safety guard red-run, the full bats and Go gates run natively; 0.1.0 installed from the public `install.sh` into a fresh home, and `mo update` moved it to 0.2.0; 0.2.0 installed the same way on 2026-11-02 (archive passed in with `--archive`, since github.com release downloads were reset on the ThinkPad's network), every command exiting 0 through `mo remove --yes`.
- **Devbox** (Debian 12 container): GNU tool behaviour and sudo password flows with a throwaway sudoers entry.
- **Real btrfs and snapper** (2026-11-02, throwaway VM with Omarchy's subvolumes and snapper config): 231 MB of old packages freed 0 MiB until the snapshot holding them was deleted, then 220 MiB; clean, uninstall, analyze and status all said so; a separate `@pkg` subvolume showed no note.
- **Real Flatpak and Snap** (2026-11-02, `real-tools.yml` on Ubuntu 24.04): a user Flatpak app listed, removed through flatpak with its data kept and then listed as an orphan, its cache cleaned, 2.11 GB of unused runtime freed; Snap's `hello-world` cache found, skipped while running in its snap scope, cleaned afterwards. Runs again whenever clean, uninstall or delete code changes.
- **CI** (`test.yml`): shellcheck, Go tests and bats in an `archlinux` container, plus a release archive installed, run and removed for a fresh user; aarch64 archive checked on an ARM runner.
- **0.3.0 source** (2026-11-02, devbox as the user `mole`): 189 bats tests and the Go tests pass, shellcheck clean; `mo purge` driven in tmux (picker, confirm, 150 MB of `node_modules` and `target` removed, project files kept). An independent review in three rounds found 22 issues (1 high: a git failure read as "nothing tracked"); 20 fixed with tests, two kept as known gaps (non-dumpable processes, below; a debug line naming the home mid-line, which no caller writes today). The Omarchy VM run was cut off when the UU link to it dropped.
- **0.3.0 end-to-end use** (2026-11-02, devbox as the user `mole`, HEAD built as a release archive and installed with `install.sh --archive`): every command run once the way a user would, in tmux for the interactive screens. `--version` (Install: Release), `--help`, main menu, `clean` dry and real (157 MB of npm, pip and Go build caches), `--gpu-shaders` (Mesa only with the flag), a whitelisted pip cache kept, `purge` dry, picker, confirm and removal (68 MB, project files kept), `--paths`, `optimize` dry and real, `analyze` TUI and `--json`, `status` TUI and `--json`, `history` text and `--json`, `--debug` log path, `remove --dry-run` and real (every path gone). One defect found and fixed: the sudo prompt read "Journal need sudo" for a single item. Not exercised here: `uninstall` (Debian has no pacman or Flatpak apps, by design), and `update` (the devbox reaches GitHub only through the Mac's proxy, which was off the home LAN; `update` passed on the Omarchy VM on 2026-11-02).
- **0.4.0 Debian and Ubuntu** (2026-11-02, released 2026-11-04 as `V0.4.0-linux`): devbox (Debian 12) real run of apt uninstall, autoclean and the optimize reports, restored afterwards; `real-tools.yml` on Ubuntu 24.04 ran a real snap (revisions, `--yes` refusal, removal) and apt (`c65db7c4`, run 41404562979). Independent review in two rounds: 9 findings, all fixed with tests (the worst: Ubuntu's resident unattended-upgrade-shutdown would have made apt read as always running). Never run on an Ubuntu desktop with GNOME and real snaps such as Firefox.
- **0.5.0** (2026-11-08, released the same day): devbox (Debian 12, user mole) fresh install of the release candidate reports 0.5.0 `Install: Release`; `mo clean` dry and real runs removed only yarn and pip caches and left Cypress, Playwright and Camoufox folders; an unreadable `purge_paths` exits 1 and keeps the file; `mo update --nightly` built `Install: Nightly`. After publishing, a fresh install of the published 0.4.0 archive updated with `mo update` to 0.5.0, verified its archive, and a second `mo update` reported the latest version; GitHub release downloads had returned 504 for about an hour first. `TestPartialNavigationRefreshRecoversCoverage` failed on TempDir cleanup in Validation and in the release run and passed on rerun: `update.go` saves the scan result in an unwaited goroutine, so the test can finish while the cache file is still being written. Test timing, not product behavior; `8d777cc8` gives the tests that apply a scan result a HOME whose cleanup retries, and 3000 rounds of that test on the devbox went from 21 failures to 0.
- **0.3.0 sudo flow** (2026-11-02, devbox, a throwaway password and `/etc/sudoers.d` entry for the user `mole`, both removed afterwards and the account locked again): `mo clean` in tmux. "Journal needs sudo" prompt; Enter shows Mole's own `Password:` line; three wrong passwords end in sudo's "3 incorrect password attempts", one "Authentication failed" line, the journal skipped and the rest cleaned; the right password says "Admin access granted"; Space skips, ESC cancels before anything runs; afterwards `sudo -n true` fails (Mole's own timestamp dropped), while a timestamp the user made with `sudo -v` beforehand is kept.
- **Three-CLI review** (2026-11-10, devbox as the user `mole`): a whole-tree review of this branch, never audited before, found that a Flatpak or Snap app's cache folder skipped the narrowing its native rules get (JetBrains LocalHistory, Lutris sign-in state), that a password typed at clean's sudo gate was read as a skip with the rest left for the shell (this replaces the two-key skip in the 0.3.0 sudo flow above), that a dangling whitelist link read as no whitelist, and that `COREPACK_HOME` or an `XDG_CACHE_HOME` inside another XDG base could make a data folder a cache root. All fixed with tests that fail on the previous code; an independent second review found three more defects in the fixes and four older ones, also fixed. 252 bats tests, the Go tests and shellcheck pass. Measured: 1000 `mole_ascii_lowercase` calls 770-792 ms to 15 ms; a 2,000-entry Trash dry run 51-54 s to 28-29 s. The sudo gate was driven on a pty with a stand-in sudo, not in a real session with a password. Follow-up the same day, by maintainer decision: `MO_PURGE_PROBE_TIMEOUT`, `MO_PURGE_WALK_TIMEOUT` and `MOLE_NO_UPDATE_CHECK` are removed (`954da7d7`), and `mo history` reads only the newest records into Bash (5 MB log: 1.8 s to 0.1 s).
- **0.6.0** (2026-11-10, devbox, Debian 12): the release archive built by `scripts/build-release.sh` installed for a fresh user with `install.sh --archive` and driven the way a user would, 49 checks, all passing: `--version` (0.6.0, `Install: Release`); a dry and a real `mo clean` outside a terminal that removed pip, npm, Go and JetBrains log caches and the Trash and kept JetBrains LocalHistory, the Playwright, Cypress and Puppeteer browsers, Hugging Face models, an unknown cache folder, the Mesa shader cache without `--gpu-shaders` and a Flatpak-shaped app cache's LocalHistory and shaders; `COREPACK_HOME=~/Documents` and `XDG_CACHE_HOME=~/.config` left Documents and a Chromium profile alone, the second named as redirected; a dangling whitelist link stopped clean and a whitelisted path stayed; `mo purge --dry-run` and `--yes` on a node project took only `node_modules`; `history`, `status --json`, `analyze --json`, `optimize --dry-run`, `uninstall --list`, `analyse`, the unknown-command exit code, `remove --dry-run` and `remove --yes`. The sudo gate ran in tmux for a throwaway user with a random password and an `/etc/sudoers.d` entry, both deleted afterwards: a password typed at once leads to Mole's `Password:` line and is not read as a skip, nothing reaches the shell, the right password prints "Admin access granted" and clean exits 0 with Mole's timestamp dropped; Enter then the password works; Space prints Skipped, asks nothing and still cleans user caches; `q` followed by more keys prints Cancelled, cleans nothing and leaves nothing for the shell; three wrong passwords end in sudo's own message, one "Authentication failed" line, the sudo items skipped and the rest cleaned. Typed at a person's pace, the first key opens the prompt and the rest goes to sudo, which answers "Sorry, try again." with nothing echoed. Keys sent in one burst in the few milliseconds between the gate's line appearing and Mole reading are echoed by the terminal, as with sudo's own prompt. Flatpak and Snap ran for real in `real-tools.yml` on `e1593dff`. Not run: the Omarchy VM, which was off.
- Not yet on real hardware: per-process GPU memory on a real GPU, AMD GPU sysfs names, every battery driver's fields.

## Measurements (2026-11-01)

- A fresh Omarchy install has little system junk: pacman cache 421 MB with one version per package (so `paccache -rk2` finds nothing), journald 225 MB, `~/.cache` 114 MB. The real space is in developer folders, mise (654 MB) and project build output, so Mole is not described as freeing tens of GB of system junk.
- On the devbox a single Rust project's `target` was 8.8 GB against 614 MB of toolchains: the case for purge when it comes.
- Before the port, `main`'s status on Linux scored a 72%-memory, swapping VM as 98 "Excellent", since memory pressure was empty there; the Linux status reads PSI and swap.

## Install channels (researched 2026-11-02)

- Today: `install.sh` from this branch, `mo update`, `mo remove`.
- AUR: `mole-cli-bin` installing to `/usr/lib/mole-cli` and linking only `/usr/bin/mo`, conflicting with `mo-bin`; `mo update` and `mo remove` would point to the package manager when pacman owns the copy. The package, its CI check and that update/remove change passed CI on 2026-11-02 and are kept off this branch until AUR registration reopens.
- Omarchy's own package repository needs the Omarchy maintainers; not asked.
- deb, rpm and Nix come with Debian/Ubuntu and Fedora support.

## Open

- AUR `mole-cli-bin`, once registration reopens.
- dnf and zypper rules (Fedora, openSUSE). Debian and Ubuntu shipped in 0.4.0; Snap and apt run for real only in `real-tools.yml`, never on an Ubuntu desktop.
- `mo uninstall --yes` run outside a terminal cannot remove a Flatpak app, because flatpak answers its own prompt with "n"; Mole reports it as not removed. Kept, since package managers keep their own confirmation.
- Hardware checks listed under Verification record.
- Purge's in-use check cannot read the working folder of a non-dumpable process (KeePassXC, ssh-agent and the like); such a process counts as working nowhere. Refusing every purge whenever one runs was judged worse, since those are not dev servers.
- 0.3.0 was released without an Omarchy VM run (the Mac was off the home LAN and the UU mapping was down); purge on real Omarchy is still unrun. Uninstall code is unchanged since 0.2.0, which ran there.
- Networks that reset github.com release downloads (seen 2026-11-02 from the ThinkPad's network, API reachable) make `install.sh` and `mo update` fail; the installer's `--archive`/`--sums` is the workaround.
