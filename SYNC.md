# Synchronization

Mole CLI (Linux) re-implements Mole's product values and safety contracts for Linux; it imports no code from other branches. This file records what was carried over, what is intentionally different, and what is still pending, for two relationships:

- Mole CLI (macOS) (`main`) and Mole CLI (Linux) (`linux`)
- Mole CLI (Windows) (`windows`) and Mole CLI (Linux) (`linux`)

Each row names the source (branch, commit or entry), the Linux status (`Pending`, `Implemented`, `Intentional difference` or `Not applicable`) with a reason, and the verification. Only a published `V*-linux` release proves `Released`.

## Intentional differences

| Contract | Status | Reason |
| --- | --- | --- |
| Shared bash core (`lib/core/file_ops.sh`) | Intentional difference | Re-implemented for GNU tools; the macOS core pins BSD `/usr/bin/stat`, whose `-f` means something else under GNU coreutils (maintainer 2026-11-01). |
| Privileged Trash staging under `/Library` | Not applicable | Linux Mole never deletes or moves arbitrary paths as root; root cleanup runs only through distribution commands. |
| Finder, TCC, LaunchServices, APFS clone handling | Not applicable | macOS-only mechanisms. |

Mole CLI (macOS) and Mole CLI (Windows) have no counterpart; every row is Linux only. Learned from ubuntu-cleaner, mostly what not to do (study ledger in `docs/oss-research.md`). Real tools on 2026-11-02, `real-tools.yml` run 41404562979 on Ubuntu 24.04 (`c65db7c4`): a local two-revision snap was reported as `sudo snap remove mole-probe --revision=x1` and kept, `--yes` refused it while `~/snap/mole-probe` held a file and removed it once empty; xterm was listed, removed through apt and then reported as an `rc` package; optimize also found the runner's own unneeded LLDB libraries, `apport-core-dump-handler` left as `rc` and `/etc/ca-certificates.conf.dpkg-old`.

## Implemented on `linux` for 0.2.0 (released in V0.2.0-linux on 2026-11-02)

Released: tag `V0.2.0-linux` on `30e358d7`, x86_64 and aarch64 archives with `SHA256SUMS.txt` (the release workflow installed each for a fresh user); `mo update` on the Omarchy VM moved its 0.1.0 install to 0.2.0 after verifying the archive. A manual fresh install from the public `install.sh` was cut off when the ThinkPad dropped off the network, then rerun on 2026-11-02 through a UU Remote port mapping: the public script (byte-identical to the branch) verified and installed the release archive into an empty home with `--archive`/`--sums`, and `--version`, `clean --dry-run`, `uninstall --list`, `optimize --dry-run`, `status --json`, `update` and `remove --yes` all exited 0. The VM's own download of the asset from github.com was reset twice on that network while the API answered, so the archive came from this Mac.

Learned from xdg-ninja, pacutils `pacreport`, rebuild-detector, lostfiles, cleansys, Spruce, Cleanr and Omarchy's own update script (study ledger in `docs/oss-research.md`). Every row was tested on the Omarchy VM (ext4). btrfs and snapper were also run for real on 2026-11-02 in a throwaway VM with Omarchy's layout and snapper config: the clean row, the freed total, the uninstall line, the analyze note, the status allocation (matching `btrfs fi df`) and a separate `@pkg` (no note) all behaved as designed. Snap and real GPU fdinfo are still verified only against fixtures.
