# Router, install, update and remove

The `install.sh` fail-closed rule, the refusal-diagnostics principle and the Windows tag filter (`get_latest_release_tag_from_git`) stay in `AGENTS.md`.

## The `mole` router

- `mole` is a **router only**: it parses args, renders the menu, and dispatches. Self-update lives in `lib/manage/update.sh` and self-removal in `lib/manage/remove.sh`; both are `source`d (not `exec`d) because the interactive menu and the update banner call them in-process.
- `VERSION=` stays in `mole` because `install.sh` reads it out of this file with `sed`. `SCRIPT_DIR=` must stay a single line-initial assignment in `mole`, with the resolver above it: `install.sh` and the test harness (`tests/update.bats`) rewrite that anchored assignment, so a second occurrence is silently rewritten too and anything resolving below it overwrites the pin.
- The installer serializes the config path as a literal Bash word under `LC_ALL=C` before escaping the sed replacement, so the pinned line is pure ASCII: bash 3.2 `printf %q` in a UTF-8 locale leaves lead bytes raw and escapes only some continuation bytes, which is not valid UTF-8, and the `VERSION=` fallback read in `install.sh` runs `sed` under `LC_ALL=C` for the same reason. Never interpolate raw path text into shell source.
- The symlink cases in `tests/cli.bats` lock the resolver, not this invariant; `install_files preserves literal shell and sed characters in config paths` and `get_installed_version fallback reads VERSION past a pinned line that is not UTF-8` in `tests/install_checksum.bats` and `remove_mole lists a launcher installed under a non-ASCII config path (UTF-8 locale)` in `tests/uninstall.bats` lock the serialization.

## Install lock and refusals (`install.sh`)

- `acquire_install_lock` reports stable reasons through `INSTALL_LOCK_FAILURE`; unsafe-ancestor variants use `INSTALL_LOCK_UNSAFE_ANCESTOR_REASON`. Each refusal keeps one factual cause line plus one cause-specific next action (the general rule is in `AGENTS.md`). `tests/install_checksum.bats` pins the branches.
- Install and update are single-flight per install directory through one target-adjacent mutex: prefer absolute `/usr/bin/lockf`; where it is absent (#1348), fall back to an atomic `mkdir` in the lock directory, reclaimed only against proof the recorded owner is gone (dead pid, or a live pid whose start time no longer matches). A lock command that *runs and refuses* is contention, a platform that never had one is not, and only a system with neither primitive is turned away. Do not build the lock wrapper as a shell array.
- **`install.sh` never uninstalls Homebrew's Mole.** A `Cellar/mole` that is not the active launcher (another copy earlier in PATH, or brew's link is missing) is reported with the exact `brew uninstall --force mole` command and the install continues beside it. Running `brew` here would delete an install this run was not asked to touch, and `brew` resets sudo's cached ticket, which breaks the pre-authenticated `mo update` handoff. Locked by `installer warns instead of uninstalling a Homebrew Mole it did not invoke` in `tests/install_checksum.bats`; the pre-auth window rule stays locked by `the update path never runs brew inside the pre-authed window`.
- **Release verification is cached once per tag per installer run.** `verify_release_asset_checksum` fetches SHA256SUMS and verifies its attestation once, caches the file and verdict for the tag, and reuses them for analyze and status; each asset still gets its own sha256 comparison, and a mismatch still aborts with no source-build downgrade. Locked by `release verification fetches SHA256SUMS and its attestation once per tag` in `tests/install_checksum.bats`.

## Self-update (`lib/manage/update.sh`)

- `lib/manage/update.sh` owns self-update, registry/bootstrap replacement, and self-heal fallback behavior. Preserve fail-closed version checks and test both normal update and broken-bootstrap recovery with `MOLE_TEST_NO_AUTH=1 bats tests/update.bats tests/cli.bats`; `tests/cli.bats` is what runs `tests/main_menu_pty.py`, so `bats tests/update.bats` alone skips the gate, exit-status, signal and perl-fallback cases.
- **Self-heal.** The `mo update` self-heal fallback (`_update_self_heal_reinstall`) streams install.sh from `main` straight into bash with no local temp files, because a broken installed bootstrap cannot fix itself (#1297). Assert stable success against the installed binary's bounded version response, never installer output, and keep `install.sh`'s own `--version` / `--help` verification probes bounded. Nightly success additionally requires a per-attempt install receipt; pin the source archive to the resolved commit when HEAD is known, and never reuse an older `COMMIT_HASH` when it is not. Locked by `tests/update.bats` and `tests/install_checksum.bats`; the V1.47.1, #1297, and #1348 history is in `.claude/skills/bugs/references/shell-and-test-pitfalls.md` section 4.
- **Launcher signals.** The interactive command wrapper installs cancellation traps before launching a child, retains signals received before PID assignment, and forwards them once both the PID and the Perl launcher readiness signal are available; asynchronous Bash children initially ignore INT. Before notifying readiness, the launcher also unblocks inherited TERM. The inherited-mask case in `tests/main_menu_pty.py` pins that boundary. `tests/main_menu_pty.py` expands that startup window with builtins; a foreground sleep would change trap scheduling and hide the race.
  - The launch, the readiness wait and `wait` run inside one `2> /dev/null` group with the child's own stderr on fd 9; the after-launch case in `tests/main_menu_pty.py` pins it. Settle the one readiness notification before entering Bash 3.2 `wait`. The readiness-handler window and launcher-exits-before-ready cases pin this ordering. The stories behind these three rules are in `.claude/skills/bugs/references/shell-and-test-pitfalls.md` (Focused pitfalls).
  - `run_mole_command` runs a plain `exec` when `/usr/bin/perl` is missing or the target is not an executable file, and a terminal Ctrl-C can reach a command twice (tty broadcast plus the forward), so command INT handlers must tolerate a repeat.
- **Update notices.** Maintenance-command notices only run for interactive output. Background checks cache successful results for one day and unknown results for one hour, retaining known notices on network failure. The throttle key hashes version, channel, commit and `SCRIPT_DIR`, never the invoked name, so `mo` and `mole` share one lookup; a notice that offers the running or an older version is dropped when read, and an unwritable cache or unreadable install receipt stays silent. Stable discovery must use published release metadata or its release redirect, never the version on main; Homebrew notices use the published formula. Keep machine-readable output silent, preserve command exit statuses and cancellation, and refresh an idle menu without changing ESC decoding. The main menu colors the command at render time (`_main_menu_update_notice`) while the cache and the after-command line stay plain.
- Locked by `tests/update.bats` (throttle, notice cache, stale-notice and nightly cases), by `tests/main_menu_pty.py` through `tests/cli.bats` (gate, exit status, signal forwarding, repeated INT, perl fallback, idle refresh) and by the `show_main_menu` and `interactive_main_menu` cases in `tests/cli.bats`. `read_key` ESC decoding has no timing test, so the ESC timeout rule in `AGENTS.md` is its guard (`.claude/rules/core.md`).

## Self-removal (`lib/manage/remove.sh`)

- **`mo remove` preserves non-default config roots.** `install.sh --config` can merge into a shared directory such as `~/.local`; a Mole library and familiar top-level `bin` / `lib` names do not prove ownership of their contents. Do not move a custom root wholesale or substitute another install's default config when ownership is unknown. Resolve the pinned install separately from source checkout and Homebrew layouts, show the custom path as kept for manual review, and move only the reserved `~/.config/mole` root to Trash.
- A filename of `mo` or `mole` is not launcher ownership: inspect released launcher signatures without executing the candidate, byte-wise (`LC_ALL=C` awk), so a launcher whose pinned path is not valid UTF-8 is still recognized, and recheck after confirmation before unlinking aliases or entrypoints. The channel receipt still follows the selected install before the default.
- Locked by the `#1589` cases in `tests/uninstall.bats` and `tests/update.bats`, plus `remove_mole recognizes a launcher already pinned with invalid UTF-8 (UTF-8 locale)` and `remove_mole PATH discovery lists genuine launchers and never foreign commands` in `tests/uninstall.bats`.
- **Shell integration.** `mo completion` and `mo remove` share `MOLE_COMPLETION_LINE_PATTERN` and `mole_resolve_link_chain` in `lib/core/base.sh`; do not duplicate them. Match only the exact `# Mole shell completion` marker and whole generated eval/source/Fish lines. Keep quoted mentions and mixed user commands: the former boundary `(^|[^[:alnum:]_-])(mole|mo)[[:space:]]+completion` spares `gizmo completion zsh`, but a `(mole|mo) completion` mention alone does not prove ownership. For `~/.zshrc`, `~/.bashrc`, `~/.bash_profile` and `~/.config/fish/config.fish`, follow the full symlink chain and rename over its final target, preserving all links and target mode. Self-removal also deletes `~/.config/fish/completions/{mole,mo}.fish`; dry-run only lists changes. Log each rc edit, Fish deletion, launcher and cache removal through `log_operation`. Removal failures name the path and exit nonzero. Locked by `remove_mole preserves multi-level rc links and unrelated completion tools`, the `remove_mole` completion and partial-failure cases, and `completion removal preserves quoted and mixed commands byte for byte` in `tests/uninstall.bats`, plus `completion normalization keeps user lines mentioning Mole completion` in `tests/completion.bats`.
- **Removal confirmation needs a real terminal unless a test flag is set.** A failed or empty `read` is not Enter: `mo remove` exits 1 when stdin is not a TTY under production, while `MOLE_TEST_MODE` may drive the prompt through a pipe. Locked by `remove_mole without a terminal exits nonzero and removes nothing` in `tests/uninstall.bats`.
- `mo remove` keeps `~/Library/Logs/mole` (operations.log rule in `AGENTS.md`).
