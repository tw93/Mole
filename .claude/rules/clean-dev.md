# Developer and toolchain caches (`lib/clean/dev.sh`)

General clean target policy, including the owner-command rule, is in `.claude/rules/clean.md`.

- `lib/clean/dev.sh` owns developer-tool cleanup, language/toolchain caches, AI agent caches, and Codex runtime handling. Run `MOLE_TEST_NO_AUTH=1 bats tests/clean_dev_caches.bats tests/dev_extended.bats tests/clean_developer_state.bats tests/manage_whitelist.bats`.
- Its DeviceSupport cleanup covers every platform the uninstall sweep in `lib/core/app_protection.sh` knows, with the same keep-newest rule; the two lists drifted once (`db2e462e`, `d9329649`), and `clean covers every DeviceSupport platform the Xcode uninstall sweep knows` in `tests/dev_extended.bats` now reads both.
- `clean_dev_jetbrains_toolbox` only strips whitelist patterns that start at its own apps root, so the broader JetBrains data row and the default `Application Support/JetBrains*` pattern still hide old Toolbox IDE versions; `JetBrains data row hides old Toolbox IDE versions from cleanup` in `tests/manage_whitelist.bats` pins the row case, so change that test together with the bypass if the bypass is widened.
- The Gradle candidate listing puts the small groups before the build cache, which can hold thousands of entries: whitelisted entries are settled before the roughly 10 ms `should_protect_path` probe, and an exhausted filtering budget keeps only the build cache group.
- Keep AI-tool cache cleanup conservative. Claude Code, opencode, Copilot CLI, Zed, Warp, Ghostty, and similar developer tools may have active versions, config, credentials, or session state that must not be removed accidentally.
- `clean_t3code_desktop_caches` takes only `Cache` and `Code Cache` under `Partitions/t3code-preview-*` of the `t3code-v2` and `T3 Code (Alpha)` profiles, while no T3 Code app runs. `should_protect_path` does not cover these profiles, so that exact list is the whole boundary: sign-ins, IndexedDB and Service Worker data stay, and `~/.t3` is never a target (its worktrees are `mo purge` scope). Locked by the `clean_t3code_desktop_caches` cases in `tests/clean_ai_cli_caches.bats`.
- **Docker is asked only on a local engine, and Mole prunes only what the engine rebuilds.** Every Docker query (`docker system df` in Large files, `docker ps` in `mo optimize`, the prune) first reads the endpoint through `mole_docker_endpoint_is_local` in `lib/core/common.sh`, which runs `docker context inspect` (local configuration, honours `DOCKER_HOST`, never dials the engine); anything but a `unix://` socket, or an unknown answer, skips the query, so a remote context neither reports another machine's storage nor hides the Docker Desktop data row (#1922). `clean_docker_unused_data` then runs `docker builder prune -f --filter until=168h` and `docker image prune -f` (dangling only) only after `docker info` answers, so a stopped Docker Desktop is never started; containers, volumes, networks and tagged images are never touched, and no config option exists for any of this. The engine serialises prune against running builds, so there is no process guard. `docker builder` is `docker buildx` once the plugin is installed and prunes the selected buildx builder, which can be a cloud or remote one under a local context, so the build cache prune runs with `BUILDX_BUILDER` set to `docker context show` (the local context's own builder; the legacy builder ignores it) and is skipped when that name is unknown. On the classic image store an image pulled only by digest and used by no container counts as dangling and goes too; that is accepted, since a registry pull restores it. Its whitelist row is the Docker Desktop data folder, every prune that exits 0 logs `REMOVED` (with its size when Docker printed one), a timeout skips that one prune and a signal cancels; the dry run says `would prune` without a size, like the other owner rows. Locked by the `clean_dev_docker` cases in `tests/clean_dev_caches.bats` (`clean_dev_docker pins the build cache prune to the local context builder` for the builder), `large files never queries a remote Docker engine (#1922)` in `tests/clean_user_core.bats` and `idle VM never asks a remote Docker engine about containers (#1922)` in `tests/optimize_perf_diagnosis.bats`; `docker` is a fail-loud stub in `tests/helpers/common.bash`, so a test that forgets its double can never prune the host.

## Recovery contracts

- Owner-command rows (`clean_tool_cache`, `clean_dev_go`) measure the root before and after the command and show and count only the bytes that disappeared; roots outside `$HOME` (the Nix store) and links are not measured, a failed measurement shows no size, and a signal while measuring cancels before the owner command starts. Dry runs still say `would clean`, since a prune's effect cannot be known ahead. Locked by `owner cache rows show and count only the bytes their command removed` and `an interrupt while measuring an owner cache stops before the owner command` in `tests/clean_dev_caches.bats`.
- uv, npm, pip and mise owner cache commands require a successful absolute-root query (or mise's explicit absolute `MISE_CACHE_DIR`). Failed, empty, relative or multiline answers skip that owner command; a signal still cancels. Never whitelist a guessed default and then let the owner mutate its separately configured root. Known npm default residuals keep their existing safe-clean guards. Locked by the four `owner cleanup requires a confirmed cache root` cases in `tests/clean_dev_caches.bats`.
- `bun pm cache rm` runs only on a confirmed absolute root from `bun pm cache` (a root of `/` is refused, since it strips to the empty path `clean_tool_cache` skips policy for), through `clean_tool_cache`'s whitelist and physical-root checks, and only while `bun_process_state` (bun and bunx, since a process keeps the name it was started by) reports idle, checked again at the command; a failed or timed-out run keeps that cache and nothing falls back to deleting it directly. When uv or bun itself is unusable (not on PATH, or `--version` fails), and for the default bun root a custom configuration leaves behind, the cache is removed directly only after `uv_process_state` / `bun_process_state` confirm no owner process runs, because a copy outside Mole's PATH may still hold it; running or unknown keeps it. Locked by `bun owner cleanup requires a confirmed cache root and an idle bun`, `bun process probe also sees bunx`, `clean_dev_npm keeps the bun cache when the bun cache command fails or times out`, `clean_dev_npm never removes the bun cache directly after its owner command stops` and `uv and bun caches without a usable owner are cleared only when no owner process runs` in `tests/clean_dev_caches.bats`.
- Conda validates every `pkgs_dirs` entry from one successful `conda info --json` snapshot before running its owner cleanup. An absent, empty, invalid or partially readable list skips the command; any whitelisted root or descendant protects the entire command. Locked by `conda owner cleanup protects every configured package cache root` in `tests/clean_dev_caches.bats`.
- Owner-cache policy checks both the configured path and its physical location, including linked ancestors and an absent leaf below an existing parent. Protected or unresolved roots skip the owner command; Conda applies this to every configured root. The confirmed-root cases also cover linked roots and protected state.
- Physical-root resolution preserves signal statuses from its subshell so an interrupted lookup cancels the caller instead of silently continuing with later cleanup. Ordinary resolution failures still retain only that cache. Locked by `owner cache physical resolution preserves interruption and ordinary failures` in `tests/clean_dev_caches.bats`, using executable owner and resolution stubs.
- Yarn Berry's `~/.yarn/berry/cache` archives are installed dependencies read directly by Plug'n'Play projects, even when no Node or Yarn process runs. Keep the root and descendants out of `clean_dev_npm` and protected by the clean-only `should_protect_path` policy, independent of default or custom whitelist files; explicit uninstall retains its separate policy. Classic's `~/Library/Caches/Yarn` remains cleanable. The obsolete Berry whitelist menu row stays absent, while saved patterns remain custom entries. Locked by `clean_dev_npm keeps Yarn Berry dependencies and cleans only Yarn Classic` and the two `Yarn Berry producer and sink preserve dependencies` cases.
- Jupyter runtime connection files are live session state. Keep `~/.jupyter/runtime` out of the Python cleanup producer and protect its root and children at the shared clean boundary; explicit uninstall retains its separate policy. Locked by the two `Jupyter runtime` cases in `tests/clean_developer_state.bats`.

- **Classify cleanup by recovery contract, not by directory name or download cost.** Re-downloading is a real cost but not an automatic veto when the user explicitly runs `clean`: Go's module cache is owner-documented, machine-resolvable, and independently whitelistable, so it is reset through `go clean -modcache`.
- Directly consumed or mixed-state stores still stay: `registry/src`, Cargo `git`, `$DENO_DIR`, `~/.ivy2/cache`, `~/.m2/repository`, `~/.nuget/packages`, `~/.cabal/packages`, and `~/.cpan/sources`. Cargo's compressed `registry/cache` is redundant with extracted sources, while Cargo 1.88+ owns age-aware GC for sources and git dependencies.
- Downloaded model and experiment roots (`~/.cache/huggingface`, `~/.cache/torch`, `~/.cache/tensorflow`, `~/.cache/wandb`) and toolchain payloads (`~/.sbt/boot`, `~/.sbt/launchers`, `~/.stack/programs`) stay off the blanket delete path. `DENO_DIR` is review-only because the owner command removes the entire root, including origin storage and downloaded runtime payloads.
- A default whitelist row is not protection once the user saves a custom file, so fix the delete path itself and remove whitelist inventory entries for targets Mole no longer deletes. Each inventory row names a path a cleanup actually consults, and `package-manager whitelist rows protect the paths their cleaners delete` and `whitelist inventory has no row for a path no cleanup consults` in `tests/manage_whitelist.bats` run the real `clean_dev_*` cleaners for pip, Yarn, RubyGems and Podman against their rows. The Ollama default lives only in `DEFAULT_WHITELIST_PATTERNS`, and a saved line for a dropped or respelled row stays as a custom pattern (`saved lines for dropped whitelist rows survive a menu save and keep protecting`).
- Nix cleanup is `nix-store --gc` under the owner-command timeout, which removes only store paths no GC root references; `nix-collect-garbage --delete-older-than` also deletes every profile and home-manager generation past the age, the user's rollback points, so Mole never runs it. Locked by `clean_dev_nix collects only unreachable store paths under a timeout` and `clean_dev_nix dry run runs no Nix command` in `tests/clean_dev_caches.bats`.

## Xcode and simulators

- **Join simulator data on `runtimeIdentifier` from `-j` output, never on a printed runtime name.** The two listings title the same runtime differently, so a name join offers `simctl runtime delete` for a runtime its simulators still bind (story in `.claude/skills/bugs/references/shell-and-test-pitfalls.md` section 7). A reclaim recommendation additionally needs `state: Ready`, `deletable: true`, and exactly one installed image serving that identifier, because the device list cannot say which of two images its devices belong to. Locked by the `#1505` test in `tests/clean_orphaned_runtimes.bats`.
- **simctl waits for Xcode's own first-launch setup.** On an Xcode whose first-launch packages are not installed, any simctl call asks macOS to install CoreSimulator behind an administrator prompt, which a user who had skipped sudo saw appear mid-`mo clean`; users pinned to a simulator version must never have components installed by a cleanup run. `_resolve_simctl_developer_dir` accepts a developer dir only after its `xcodebuild -checkFirstLaunchStatus` returns 0 within the medium probe bound, so every simctl caller, including the booted-device guard, inherits the gate and the skip stays quiet; a signal during that check cancels the run instead of reading as unfinished setup. Locked by `simctl stays untouched while Xcode first-launch setup is unfinished` in `tests/dev_extended.bats`.
- **Every simctl read goes through `_run_simctl`.** `clean_dev_mobile` pins its probe count in `tests/dev_extended.bats`; a raw `run_with_timeout ... xcrun simctl` bypasses the stub, so added probes stay invisible to that assertion instead of being weighed by it.
- **Per-device simulator data is removed by whole leaf, only on a shut-down device.** `_SIMULATOR_DEVICE_LEAVES` lists the leaves Mole Mac also takes (MobileAsset `AssetsV2`, `var/db/diagnostics` and `uuidtext`, `Library/Caches`, the `PRBPosterExtensionDataStore` poster store); a device counts only when its `device.plist` reads `state` 1 and not `isDeleted`, an unreadable plist leaves it alone, and the delete-time guard reads it again and skips just that leaf. Read one validated XML snapshot and inspect root-dictionary types: `state` must be integer 1 and `isDeleted` must be absent or boolean false. Never infer absence from a failed `plutil -extract` command or its diagnostic output. Locked by `simulator metadata uses root XML types rather than missing-key diagnostics` in `tests/clean_app_caches.bats`; metadata timeouts retain the device, while signals propagate through discovery, the final guard and `clean_xcode_tools` before another device is processed. Locked by `simulator device metadata timeouts retain the device and signals stop later devices` in `tests/clean_app_caches.bats`. The poster store goes whole or not at all: with it gone the next boot rebuilds the gallery as a new device does (a custom wallpaper resets), while removing only its `descriptors` left `staticdescriptors` empty and the gallery failing to render (iOS 27.1, 2026-10-28). Never add `data/Containers` (installed app copies and their data) or other `data/Library` siblings to that list. The leaves also pass the shared protection and whitelist filter before the run decides there is simulator work, so a fully whitelisted simulator never reports a skip. Locked by `clean_xcode_tools removes per-device simulator data whole, only on shut-down devices`, `simulator device leaves refuse links on the way and recheck the device before deleting`, `clean_xcode_tools reports no simulator skip when every device leaf is whitelisted` and `simulator device leaves go through the real sink, skipping only a device that booted` in `tests/clean_app_caches.bats`.
- The CoreSimulator `Volumes` and `Cryptex` roots are Apple-owned and left alone, neither deleted nor listed: mount absence does not establish ownership or obsolescence. Unused runtimes are surfaced through `simctl` instead.
