# Install

- `install.sh` (served from this branch at `raw.githubusercontent.com/tw93/Mole/linux/install.sh`) takes the newest exact `V*-linux` tag from the releases list, checks the archive against `SHA256SUMS.txt`, unpacks into `~/.local/share/mole` beside the old copy, runs it, then swaps it in and links `~/.local/bin/mo`. `mo update` reruns a copy of it (skipping prerelease tags, refusing to run from a tree that is not the installed one, `--force` reinstalls; versions compare by their numeric X.Y.Z core only, so a prerelease of the latest core or a broken VERSION is replaced and only a core above the latest is refused as a downgrade; the main menu, only in the installed tree (`mole_runs_installed_tree`, the same check), checks for a newer release in the background at most once a day, cached in `~/.cache/mole`, off with `MOLE_NO_UPDATE_CHECK=1`); `mo remove` deletes only that tree, the two links when they point at it, and Mole's own config, cache and state folders. `mo update --nightly` (`install.sh --nightly`, maintainer 2026-11-04) installs the newest `linux` commit as `<core>-nightly.<sha7>` with a `NIGHTLY` receipt holding the full hash, from the codeload source archive pinned to that hash (no checksum exists for it, as on `main`), plus the three Go helpers built from that source: the user's `go` first, else, only when that go is missing or older than go.mod's `go` line, the newest stable Go from go.dev (golang.google.cn when go.dev fails), checked against the SHA256 the same site lists and kept as one toolchain in `~/.cache/mole/go` (a cached one is used when neither listing answers), modules beside it with `-modcacherw` so `mo remove` can delete them, the build cache and Mole's go's config folder (its telemetry) in the run's temp folder, `GOTOOLCHAIN=local`, `GOWORK=off`. Every path must end with runnable `trash-go`, `status-go` and `analyze-go` or nothing is installed, and a source whose `install.sh` is not this branch's is refused. The staged file list in `install.sh` mirrors `scripts/build-release.sh`; a new top-level runtime file goes into both. `GOPROXY` is the user's (environment or `go env -w`), else proxy.golang.org when it answers within 8 s, else goproxy.cn: from China proxy.golang.org hangs instead of failing, so go's own `|` fallback never fires (240 s without finishing against 3 s, devbox 2026-11-04), and go.sum pins every module either way. When no helper build works, the latest release's checksum-verified helpers are used and named; with neither, nothing is installed. A plain `mo update` on a nightly switches back to the release, even when the nightly carries the core of a release still in draft, and the menu notice compares a nightly by its core. Stable installs never touch Go. Locked by the nightly cases in `tests/update.bats`.
