# `mo purge` and `mo installer`

## Purge (`lib/clean/project.sh`)

- `lib/clean/project.sh` owns purge discovery, project artifact filtering, purge menus, and purge config. Run `MOLE_TEST_NO_AUTH=1 bats tests/purge.bats tests/purge_config_paths.bats`.
- **Git worktree staleness is not decidable.** Clean only whitelisted rebuildable artifacts inside a worktree, never the worktree itself, and never emit a "safe to delete" verdict. Branch/remote heuristics fail on detached worktrees, ordinary status hides ignored files, and ignored entries may be the only copy of private state. A status surface may report blockers only: dirty, unpushed, locked, or ignored entries outside `MOLE_PURGE_TARGETS`.
- Purge discovery skips dot-directory containers by design. Add each supported container, such as `~/.codex/worktrees` and `~/.t3/worktrees`, explicitly to `MOLE_PURGE_DEFAULT_SEARCH_PATHS`; do not broaden discovery to all dot directories. That list also feeds `discover_project_cache_roots` in `lib/clean/caches.sh` (the `mo clean` project-cache sweep) and the purge hints in `lib/clean/hints.sh`, so a new container reaches those too. The scan layer already handles hidden descendants once their parent container is known, while project roots deeper than the existing two-level probe remain intentionally out of scope.
- **A purge target is never a container.** `is_project_container` rejects any basename in `MOLE_PURGE_TARGETS`, not a separately maintained list of package directories, so a stray `~/node_modules`, `vendor/`, or `Pods/` is never scanned as a set of project roots whose internal `dist/` and `build/` reach the delete list. A directory that legitimately shares an artifact name stays reachable by listing it in `~/.config/mole/purge_paths`, which bypasses discovery; do not add a flag for it. This one probe is the whole surface: the other three scan-root entry points in `lib/clean/project.sh` are the maintainer default list, the user config file, and the consumer of discovery. Locked by the two `#1459` tests in `tests/purge.bats`; the story is in `.claude/skills/bugs/references/deletion-evidence-and-final-sink.md` section 13.
- **Purge candidate protection.** Purge candidates with deployment keypair files, nested Git repositories, or Git-tracked content are protected at discovery and immediately before deletion.
  - **An artifact in use is protected.** `is_protected_purge_artifact` asks `purge_artifact_in_use` for every candidate, so discovery, the shared recheck before a real or dry run, and the final sink agree: any file descriptor, mapped binary or cwd inside it held by a current-user process other than Mole (`lsof` with no fd limit, in both spellings), or a command line naming it (physically or through the scanned root), keeps it; what counts as Mole is the same as for the project process check below. A selected artifact that is refused says so and what to do. `target`, `.build`, `venv`, `.venv` and project-local `DerivedData` with their markers also stay while their project runs (`purge_node_project_running`). Discovery reads one lsof snapshot per filter pass, taken before its workers start, so a large root does not pay a whole-system listing per candidate; the recheck and the sink always probe live. The boundary: root and other users' processes are not visible, and an activated venv whose interpreter lives elsewhere leaves no evidence unless its cwd is in the project. Locked by `purge_artifact_in_use detects open file descriptors mapped executables cwd and args`, `purge_artifact_in_use sees real holders above fd 999 and on non-ASCII paths`, `purge dry run and real run refuse an in-use artifact the same way`, `purge discovery reads one lsof snapshot per filter pass` and `purge protects Rust target Python venv Swift .build and project DerivedData while active` in `tests/purge.bats`.
  - A SwiftPM scratch root is `.build`, or a `--scratch-path` directory whose regular `CACHEDIR.TAG` names Swift Package Manager and whose name is no other purge target. Once it holds dependencies (non-empty `checkouts/` or `repositories/`), offering it whole trips the nested-repository guard and would force a network re-clone, so discovery offers its compiler and index outputs instead (`MOLE_SWIFTPM_BUILD_OUTPUT_DIRS`), one level further for an `index-build` that resolved its own dependencies, and leaves `checkouts/`, `repositories/`, `artifacts/`, `workspace-state.json` and other siblings alone. A file named `workspace-state.json` alone proves nothing, and a root with no dependencies stays one candidate. A whitelist entry on the scratch root also keeps its outputs, since a glob entry gives children no inheritance. Each output passes authored-content checks plus project and `--scratch-path` process probes at discovery and at the final sink. Locked by `purge decomposes SwiftPM scratch roots with package checkouts into compiler output subdirs`, `purge never decomposes a non-SwiftPM target holding a workspace-state.json`, `purge keeps a dependency-free SwiftPM root as one candidate`, `purge decomposes an index-build holding its own checkouts`, `a whitelisted SwiftPM scratch root keeps its decomposed outputs` and `purge protects SwiftPM compiler output subdirs while project or scratch-path processes run` in `tests/purge.bats`.
  - `node_modules` also requires a readable project manifest, lockfile, and matching npm/pnpm/Yarn install record. Package files newer than that record remain protected, excluding the disposable top-level `.cache` directory. Running project cwd/arguments and incomplete process visibility preserve the candidate even after explicit recent selection. Run the final activity walk before the final protection probe so its project-process check follows all recursive scans and precedes the inode rebind; the real-sink `purge final node owner after activity scan` cases cover running, unknown, idle, and signals. Keep the existing seven-day age threshold; install provenance is a separate condition. The process check compares both the raw path and lsof's C-locale spelling (`\xHH`, a doubled backslash), because purge runs under `LC_ALL=C`, and matches a command line case-blind, in either Unicode form, through the `/private` alias, and with any delimiter a file name cannot continue into. A command line spelling the project through a symlinked root is not matched; its cwd or open files still are. A hit counts unless it has exited or is Mole's own: itself, what it started, and the unbroken chain of shells that started it. The first non-shell ancestor ends that chain, so an Electron app whose terminal runs Mole still protects its project. The process table is read after the probe; a failed read is unknown and a signal stays a signal. Locked by the `purge node_modules` and `purge node project process` tests.
  - Never invoke Apple's `/usr/bin/git` shim to discover whether CLT is installed. Resolve the selected developer directory read-only and use its real Git executable; absent tools leave the content verdict unknown without opening an installation prompt. A non-shim Git selected through PATH keeps its existing behavior.
  - Use physical Git ancestry, a full-path `:(top,literal,icase)` pathspec from `mole_git_path_spec` (literal so glob characters match nothing else, case-blind because the default volume is case-insensitive and the index may keep another spelling of a renamed folder), inherited pathspec switches unset, and disabled fsmonitor hooks.
  - The content walk runs on the tree-walk budget (`MOLE_TIMEOUT_HINT_SCAN_SEC`), and a probe that times out or fails is status 2, not evidence: the candidate is kept, discovery passes it through, the review step prints `Could not inspect X; kept` and marks the run incomplete, and the sink still refuses it. Signals remain cancellation statuses through Git/find probes, protection predicates, workers, review, and the final sink; never collapse them into status 2 or a normal protected result. Never fold that state into a silent drop.
  - Discovery runs these probes in a pool of at most four per scan unit and publishes them in input order only after every probe finished; a missing result counts as unverified, and a scan cancelled during its last probes makes the filter return 130 with nothing written. `scan_purge_targets` writes the verified sidecar only when its caller names one as a third argument, and that caller removes it. The review before the menu reuses discovery's clean verdict from the same run and walks again only candidates without one; the recheck before removal and the final sink guard always probe afresh.
  - Non-interactive purge requires explicit `--yes`; `--dry-run` remains read-only without it.
  - Locked in `tests/purge.bats` by `purge content probes never run more than four at a time and keep input order past the pool`, `purge content probe signal inside a full pool stops the filter with nothing published`, `purge content probe filter publishes nothing when the sentinel goes away during the last probes`, `scan_purge_targets leaves a verified sidecar only for the caller that names one` and, for the pathspec, `purge protects tracked source under a folder renamed only in case`.

- **A configured root whose single scan times out is scanned again one direct child at a time (#1666).** One `purge_paths` entry holding 135 projects is one walk with one `MO_PURGE_SCAN_TIMEOUT_SEC` budget, so a single slow project skipped every sibling. Every root is still scanned first as one unit, exactly as before; a root that completes keeps that speed and output. Splitting every root up front was rejected: a flat root with 2000 small children took 54 s instead of 2 s, because each child costs its own processes.
  - Only a root that is not itself a project and whose single scan returned 124 falls back. Its partial output is discarded, `_purge_list_scan_units` lists the children the root walk would enter (no pruned names, online-only folders, purge targets, symlinks or files), and each child is re-scanned in the shared pool with its own budget. The fallback is capped at that budget times the scan slots; a child that times out or cannot start in time is reported as skipped by its own path. A project root, or a root whose listing fails or has no such child, keeps its timeout and is reported as before.
  - The configured root stays the safety root: `scan_purge_targets` takes the unit as its fourth argument and keeps depth limits and `is_safe_project_artifact` relative to `$1`, so a direct-child artifact of a non-project root is still refused. Only completed units publish, and a root binds candidates when it is unchanged and at least one of its units completed. The skipped list prints at most ten paths plus an `and N more` line; the heading keeps the full count.
  - Each unit is walked by one `find` that prints both target directories and `CACHEDIR.TAG` files, split afterwards by depth (targets to depth 6, tags from depth 2 to 7 of the configured root). Prune names and the dataless prune now also apply to tags at depth 1, which keeps a cache tag inside a top-level `.git` or `Library` out of the menu. The fd path still makes two calls per unit.
  - Locked in `tests/purge.bats` by `purge falls back to child units when a container root times out and keeps completed siblings (#1666)`, `purge scans a container root that completes as one unit with one find call (#1666)`, `purge keeps target and CACHEDIR.TAG depth coverage when walking scan units (#1666)` (both as one unit and through the fallback), `purge never offers a CACHEDIR.TAG directory inside a depth-one .git or Library (#1666)`, `purge container expansion keeps the root's safety rules for its children (#1666)`, `purge removes every scan unit temp file when one unit is cancelled (#1666)`, `purge reports container children left unscanned at the root cap by path (#1666)`, `purge stops running scan units when a later root listing is interrupted (#1666)` and `purge prints at most ten skipped child paths and keeps the full count (#1666)`.

## Installer (`bin/installer.sh`)

- `bin/installer.sh` owns installer discovery, immutable delete-plan validation, the paginated selection flow, and incomplete-cleanup exit semantics. Run `MOLE_TEST_NO_AUTH=1 bats tests/installer.bats tests/installer_fd.bats tests/installer_zip.bats`.

- Installer menu selection and final deletion confirmation require a successful read. EOF cancels at either boundary, never acts as Enter, even after a selection exists. Locked by `installer selection EOF never confirms the menu or deletion` and `installer final confirmation refuses EOF after a valid selection` in `tests/installer.bats`.
